# 压缩器 A/B 实验记录

> 版本 0.4.0 · 2026-11-25 · 工具 `context_hub_abtest`

## 目的

在**不替换原生 compaction 服务**的前提下，先回答一个更小的问题：把压缩提示词从「原生式 7 段」换成「记忆感知 8 段（含用户约束）」，摘要质量是否更好？只有提示词胜出，才值得去动服务替换。

## 方法

`context_hub_abtest` 取会话尾部最近 N 条 user/assistant 消息（跳过 context-hub 自己的注入），拼成输入，然后用当前会话的真实模型路由跑两次 `ctx.llm.stream`：

- **A（原生式）**：Primary Request and Intent / Key Technical Concepts / Files and Code / Errors and Fixes / Pending Jobs / Current Work / Next Step。
- **B（记忆感知 8 段）**：用户目标 / 用户约束 / 关键技术 / 文件与代码 / 错误与修复 / 未完成事项 / 当前进展 / 下一步；提示词额外要求保留绝对路径、命令、配置键、数值阈值、错误原文、决策理由，冲突时以对话为准。

A/B 都收到同一份带「记忆候选」的 transcript（`store.search()` 取 5 条，附在「--- 记忆候选 ---」块），因此差异只来自 8 段提示词结构，不能归因于「是否注入记忆」。

指标：

- **段覆盖率**：输出里出现了几个要求的标题；
- **来源覆盖率**：摘要词元与会话输入的词元交集 / 输入词元数（衡量“有没有漏掉输入里的东西”，不衡量语义正确性）；
- **长度、耗时**；工具同时把结果写进 `context_events`（kind=`abtest`）。

## 结果（2026-11-25，deepseek-flash，20 条消息 / 6036 字符）

| 版本 | 段覆盖 | 字符数 | 来源覆盖 | 耗时 |
| --- | --- | --- | --- | --- |
| A 原生式 | 7/7 | 1720 | 0.30 | 11.5s |
| B 记忆感知 | 8/8 | 2341 | 0.25 | 11.1s |

结论：结构上 B 完整（多出的「用户约束」段正是原生式没有的，而本轮对话里用户的偏好/禁令很多）；来源覆盖 A 略高（0.30 vs 0.25），但 A 的输出里出现了「两个版本号并存，需以代码为准」这类不确定表述，B 则把已拍定参数写成了明确约束。单次样本不足以判定优劣，机制已可复用于多轮对比。

## 踩坑：空输出

首轮 A 空、次轮 B 空，`log` 里的 chunk 统计显示空的那次把预算全花在 `reasoning-delta` 上（751 / 1198 tokens），`maxTokens: 1200` 太小，文本被挤掉。修复：`maxTokens` 提到 3000，并在空输出时重试一次；chunk 类型统计写入 `abtest` 日志便于排查。

## 局限

- 单次输入、单模型；样本代表性有限。
- 来源覆盖是词元重叠，不等于事实保真；后续应加入探针问题（问摘要回答具体事实，对照原文判分）。
- 记忆候选对 A/B 相同（本轮命中 5 条）；记忆为空时两者都只比较提示词结构。
- A/B 只比较提示词，不比较压缩触发与选区（那需要服务级替换）。

## 下一步

服务级替换已在 0.5.0 完成（`installHubCompactor()` 实例包装 `summarize()`，配置 `compactor: native|hub`，默认 native）；剩余是真实压缩事件上的 A/B 与回归：用线上 `/compact` 的输入复跑 A/B，确认 8 段结构在真实压缩上不退步。
